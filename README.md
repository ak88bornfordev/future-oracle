# Future Oracle 🔮

Тестовое задание (кейс "Future Oracle"): прототип "предсказателя будущего" для крипторынка.
Система собирает данные из двух реальных источников, сохраняет их в базу, считает
объяснимый прогноз движения цены на 24 часа - и сама проверяет себя, когда горизонт истекает.

**Стек:** PHP 8 (без фреймворка), SQLite (PDO), ванильный HTML/CSS. Внешних зависимостей нет.

⚠️ Не финансовый совет и не торговый сигнал. Реальные деньги не подключены, доходность не обещается.

## Быстрый старт

```bash
# 1. Собрать данные и построить прогнозы
php bin/update.php                # живой режим: CoinGecko API + Cointelegraph RSS
# или, без сети:
php bin/update.php --fixtures     # офлайн: реальный снапшот данных от 17.08.2026

# 2. Открыть интерфейс
php -S localhost:8080 -t public
# -> http://localhost:8080
```

Повторный запуск `bin/update.php` через 24+ часа автоматически сверит старые прогнозы
с фактом (блок "Самопроверка" в интерфейсе).

Флаг `--seed-eval-demo` (только с `--fixtures`) дополнительно создаёт один "созревший"
прогноз, чтобы блок самопроверки было видно сразу, не дожидаясь суток. Цена суточной
давности восстанавливается арифметически из реального поля `change_24h` снапшота
(base = current / (1 + change/100)), сам прогноз помечен как демо.

## Источники данных (2 реальных)

| Источник | Тип | Что берём |
|---|---|---|
| [CoinGecko API](https://api.coingecko.com/api/v3/coins/markets) | цены | цена, изменение 24ч/7д, high/low, объём, капитализация |
| [Cointelegraph RSS](https://cointelegraph.com/rss) | новости | заголовок, описание, дата, ссылка |

В `data/fixtures/` лежит реальный снапшот обоих источников (17.08.2026) - для
офлайн-демо и воспроизводимых прогонов. Схема "цены + новости" - ровно пример из ТЗ.

## Что в базе (SQLite, `data/oracle.sqlite`)

- `sources` - источники;
- `raw_records` - **сырые записи**: ответы API/RSS как есть, привязаны к запуску;
- `metrics` - **нормализованные показатели** по каждому активу;
- `news_items` - новости с тональностью, привязкой к активам и списком сработавших слов;
- `predictions` - **прогнозы** с аргументами, уверенностью, риском и результатом проверки;
- `update_runs` - **история обновлений** (когда, в каком режиме, что сделано).

Прогноз всегда считается из сохранённых данных - цифры в карточке сходятся с базой,
ничего не "появляется случайно".

## Алгоритм (прозрачный скоринг, без магии)

Итоговый скор - взвешенная сумма 4 факторов, каждый нормирован в [-1..1]:

| Фактор | Вес | Как считается |
|---|---|---|
| Импульс 24ч | 0.35 | изменение цены за сутки, ±5% → ±1 |
| Тренд 7д | 0.20 | изменение за неделю, ±10% → ±1 |
| Новостной фон | 0.30 | средняя тональность новостей по активу (словарный анализ; общерыночные новости входят с весом 0.4) |
| Позиция в диапазоне | 0.15 | где цена внутри дневного low..high: у верхней границы +1, у нижней -1 |

`score > 0.15` → РОСТ, `score < -0.15` → ПАДЕНИЕ, иначе БОКОВИК.
Веса лежат в `config.php` - их можно менять и сразу видеть эффект.

**Тональность новостей** - словарный подход: два списка слов с весами
(`src/SentimentAnalyzer.php`), поиск по границам слов. Это слабее ML-модели, но
полностью объяснимо: в интерфейсе у каждой новости видно, какие именно слова дали оценку.

**Уверенность (35-90%, никогда 100%):** база `50 + |score|*40`, штрафы за
противоречие импульса и новостей (-10), малое число новостей (-5), разнонаправленные
суточный и недельный тренды (-5).

**Риск** - не шаблонная фраза, а конкретные наблюдения: высокая волатильность,
конфликт сигналов, дефицит данных.

## Как система понимает, что ошиблась

При каждом запуске `update.php` открытые прогнозы с истёкшим горизонтом сверяются
с текущей ценой (`src/Evaluator.php`):

- РОСТ засчитан, если цена выросла > +0.3%; ПАДЕНИЕ - если упала < -0.3%;
  БОКОВИК - если движение в пределах ±0.9%;
- иначе прогноз помечается `miss`, и система пишет разбор: сравнивает знак вклада
  каждого фактора со знаком фактического движения и называет, какие факторы
  дали неверный сигнал;
- в интерфейсе - таблица hit/miss и общий hit rate.

## Структура проекта

```
bin/update.php               пайплайн: fetch → raw → normalize → evaluate → predict
config.php                   источники, активы, веса, пороги
schema.sql                   схема SQLite
src/Database.php             подключение, миграция, справочники
src/Http.php                 curl + офлайн-режим fixtures
src/Source/*.php             адаптеры источников (CoinGecko, Cointelegraph)
src/SentimentAnalyzer.php    словарная тональность + привязка новостей к активам
src/Predictor.php            скоринг, уверенность, диапазон, риск
src/Evaluator.php            самопроверка прогнозов по факту
public/index.php             интерфейс (карточки прогнозов, самопроверка, новости, источники)
data/fixtures/               реальный снапшот источников для офлайн-запуска
screenshots/                 скриншоты интерфейса
```

## Как использовался AI

Проект собран в паре с AI-ассистентом (Claude): генерация каркаса кода и UI по моей
архитектуре, ревью краевых случаев. Подход, выбор факторов и весов, схема БД и
финальная проверка - ручные. Пример находки на ревью: первый вариант анализатора
искал подстроки, и "deadline" матчился как негативное "dead" - заменено на поиск
по границам слов (см. `SentimentAnalyzer::countWord`).

## Ограничения и что бы я улучшил

- Словарная тональность груба: сарказм, отрицания ("not bullish") и контекст не
  понимает. Следующий шаг - взвешивание по свежести новости и TF-IDF, либо локальная
  ML-модель.
- Факторы коррелированы (импульс и позиция в диапазоне) - честнее было бы
  калибровать веса на истории, когда накопится статистика hit/miss.
- Один запуск = один снапшот; для продакшена нужен cron и ретраи с backoff.
- CoinGecko без ключа имеет rate limit ~30 запросов/мин - для 5 активов хватает.
